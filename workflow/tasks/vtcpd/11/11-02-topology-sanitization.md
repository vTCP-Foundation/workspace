# Description
Оновити `CoordinatorExchangePaymentTransaction::buildPathsAgain()` так, щоб він вилучав недоступні ноди та відхилені лінії довіри з топології всіх релевантних еквівалентів, спираючись на нові API. Це реалізує частину алгоритму 1 та 2 з PRD (розділ "Topology Update - Exclude Inaccessible Nodes" і "Topology Update - Exclude Rejected Trust Lines").

# Requirements and DOD

## Functional Requirements
1. Перед викликом OR-Tools зібрати список еквівалентів (`mCommand->exchangeEquivalents()` + еквівалент отримувача) і для кожного застосувати очищення.
2. Для кожного елемента `mInaccessibleNodes` видалити всі вихідні ребра через `trustLinePtrsSet(nodeID)` та `removeTrustLine`, а також вхідні ребра, використовуючи `participantsIDs()`.
3. Для кожної пари з `mRejectedTrustLines` видалити відповідне ребро в усіх еквівалентах за допомогою `removeTrustLine`.
4. Додати детальне журналювання: кількість вилучених вихідних та вхідних ребер, список виключених ліній довіри.
5. Забезпечити, що операції виконуються лише якщо колекції непорожні, щоб уникати зайвого шуму в логах.

## Definition of Done
- [ ] Код `buildPathsAgain()` очищає топологію відповідно до PRD.
- [ ] Журналювання відображає кількість вилучених елементів для кожного еквівалента.
- [ ] Функція не кидає винятків у випадку повторного виклику (ідемпотентність для вже вилучених ребер).
- [ ] Існуючі тести збираються; нові тести (із задачі 11-07) можуть покрити сценарії.

# Implementation Plan
1. **Попередня підготовка**
   - Імпортувати потрібні заголовки (якщо ще не підключені) для нових API.
2. **Очищення недоступних нод**
   - Додати цикл за `mInaccessibleNodes` після логування початку `buildPathsAgain()`.
   - Для кожного еквівалента: пройтися `trustLinePtrsSet(nodeID)` та викликати `removeTrustLine`.
   - Для вхідних ребер: ітерувати `participantsIDs()`; перевіряти кожен `trustLinePtrsSet(participantID)` на ребра, що ведуть до nodeID.
3. **Очищення відхилених ліній довіри**
   - Аналогічний цикл за `mRejectedTrustLines`; видаляти ребра у всіх еквівалентах.
4. **Логування**
   - Додати лічильники вилучених ребер та виводити їх у debug/info повідомленнях.
5. **Перевірка поведінки**
   - Тимчасово зібрати проєкт і виконати локальні тести (завдання 11-07).

# Test Plan
- **Unit Tests (покриває task 11-07)**: створити сценарії, де до `buildPathsAgain()` додаються недоступні ноди/лінії, і перевірити, що респонсивна топологія очищається.
- **Manual Smoke**: запустити транзакцію, що симулює недоступну ноду, переконатися, що лог містить очікувані записи.

# Verification and Validation

## Architecture integrity
- Огляд: підтвердити, що логіка вписується в запропонований PRD алгоритм.

## Security
- Відсутність впливу на безпеку; переконатися, що логування не містить чутливих даних (відображає лише ID).

## Performance
- Переконатися, що ітерація за `participantsIDs()` виконується лише при наявності недоступних нод; оцінити вартість для великих мереж.

## Scalability
- Оцінити поведінку для 500 нод / 100 ліній (ціль PRD) – ітерації повинні залишатися прийнятними.

## Reliability
- Перевірити, що повторне виконання не призводить до винятків і не залишає "висячих" ребер.

## Maintainability
- Код коментований за потреби, відповідає стилю; структура циклів зрозуміла.

## Cost
- Лише трудові затрати, додаткових ресурсів не потрібно.

## Compliance
- Дотримання політик `policy.md`, зокрема щодо журналювання та ідемпотентності операцій.
