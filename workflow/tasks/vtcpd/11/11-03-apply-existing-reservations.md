# Description
Реалізувати застосування поточних Incoming резервів із `mNodesFinalAmountsConfiguration` при перебудові шляхів. Це відповідає алгоритму 3 у PRD, гарантує, що вже зарезервовані потоки зменшують доступну пропускну здатність перед повторним запуском OR-Tools.

# Requirements and DOD

## Functional Requirements
1. У `buildPathsAgain()` зчитувати `mNodesFinalAmountsConfiguration`, працювати лише з записами `PathReservation::Incoming`.
2. Для кожного запису визначати `sourceID` та `targetID` за допомогою `mPaymentNodesIds`, `mPaymentParticipants`, `getOrCreateParticipantID()` та позиції вузла у відповідному `OptimalPathResult`.
3. Викликати `makeFullyUsed` для повністю зайнятих ребер (коли `reservedAmount >= maxHopCapacity`), інакше `addUsedAmount` з резервованою сумою.
4. Пропускати записи, що не мають попереднього вузла (позиція 0), щоб уникнути помилок і дублювання.
5. Журналювати кількість застосованих резервів та загальні суми для діагностики.

## Definition of Done
- [ ] Логіка застосування резервів реалізована й інтегрована в `buildPathsAgain()` після очищення топології.
- [ ] Відображення Incoming резервів не викликає винятків при відсутності шляху або попереднього вузла.
- [ ] Логи містять кількість застосованих записів.
- [ ] Інші частини `buildPathsAgain()` не змінені (окрім необхідного контексту).

# Implementation Plan
1. **Доступ до даних**
   - Переконатися, що `mPaymentNodesIds` і `mPaymentParticipants` доступні; за потреби включити заголовки.
2. **Цикл застосування резервів**
   - Додати цикл за `mNodesFinalAmountsConfiguration` після очищення топології (завдання 11-02) і до виклику `calculateMaxFlow()`.
   - Для кожного запису визначати `target` через `mPaymentNodesIds` і `mPaymentParticipants`.
   - Знайти відповідний `OptimalPathResult` (`mPathsStats[pathID]`) і позицію вузла (`positionOfNode`).
   - Для `Incoming` застосувати `makeFullyUsed` або `addUsedAmount` згідно зі значенням.
3. **Логування та лічильники**
   - Додати змінні, які рахують кількість оброблених записів та суму зарезервованих коштів.
4. **Обробка винятків**
   - Обробити випадки, коли шлях або вузол не знайдені; логувати попередження й продовжувати.
5. **Перевірка**
   - Запустити відповідні тести (завдання 11-07) після реалізації.

# Test Plan
- **Unit Tests (парні до task 11-07)**:
  - Сценарій з частковим резервом (перевірити виклик `addUsedAmount`).
  - Сценарій з повним резервом (перевірити виклик `makeFullyUsed`).
  - Сценарій з кількома шляхами, щоб підтвердити, що дублювання не відбувається.
  - Сценарій із вузлом на позиції 0 (запис пропускається без винятків).

# Verification and Validation

## Architecture integrity
- Перевірити, що логіка відповідає алгоритму 3 PRD та не змішує інші стадії резервування.

## Security
- Дані про маршрути не виходять за межі; логування не містить чутливих відомостей.

## Performance
- Переконатися, що обхід резервів виконується за час, пропорційний їх числу; відсутні зайві копії.

## Scalability
- Оцінити поведінку при 100 записах резервів (ціль PRD) — цикл має бути лінійним.

## Reliability
- Переконатися, що пропущені або некоректні записи обробляються без аварійного завершення.

## Maintainability
- Код чітко розділений, коментарі пояснюють причину фільтрації за Incoming.

## Cost
- Тільки трудові витрати; нових залежностей немає.

## Compliance
- Дотримання політик PRD і проекту щодо журналювання та обробки резервів.

# Restrictions
- Не змінювати структуру `PathReservation`; працювати лише зі споживанням даних.
- Комітити після успішного запуску відповідних тестів.
